# Симулятор бизнес-API

Первая исполняемая часть On-Prem RAG Platform: локальный REST CRUD на FastAPI и SQLite с синтетическими данными. Он представляет источник данных для будущих LLM-инструментов и служит стендом для интеграционных тестов.

Реализованы товары, магазины, поставщики, связи товар–поставщик и остатки по магазинам. Есть интерактивная документация Swagger, поиск товаров, пагинация и три бизнес-операции чтения. Отдельного пользовательского frontend пока нет: CRUD выполняется через Swagger или HTTP-клиент.

## Запуск из корня репозитория

Требуется Python 3.11 или новее. Команды PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -c tools/business-api-simulator/requirements.lock -e "./tools/business-api-simulator[dev]"
.\.venv\Scripts\python.exe -m business_api_simulator
```

Для Linux/macOS после создания venv используйте `.venv/bin/python` вместо `.\.venv\Scripts\python.exe`.

`requirements.lock` фиксирует версии зависимостей проверенного окружения. Файл используется как constraints для локальной установки и Docker; это не lock установочных артефактов всей будущей платформы.

Открыть Swagger: **http://127.0.0.1:8081/docs**. Выберите операцию, нажмите `Try it out`, заполните поля и нажмите `Execute`. OpenAPI-контракт доступен по `/openapi.json`, проверка состояния — `/health`.

У Swagger UI стандартная загрузка JS/CSS с внешнего CDN; сам REST API обрабатывает данные локально. Начальная установка Python-зависимостей также требует доступа к пакетному реестру.

Другой порт или отдельная база:

```powershell
.\.venv\Scripts\python.exe -m business_api_simulator --port 8082 --database data/another-demo.sqlite3
```

Новая база без демонстрационных данных:

```powershell
.\.venv\Scripts\python.exe -m business_api_simulator --database data/empty.sqlite3 --no-seed
```

Также поддерживаются `SIMULATOR_DATABASE_PATH` и `SIMULATOR_SEED_DEMO=true|false`. Параметр `--no-seed` имеет приоритет над переменной окружения. Путь по умолчанию — `data/business-api.sqlite3` относительно текущего каталога.

## Запуск через Docker Compose

Из корня репозитория:

```sh
docker compose up --build -d
docker compose ps
```

Внешний порт привязан к `127.0.0.1:8081`. Из контейнерной сети источник доступен по `http://business-api-simulator:8080`, как в примере локального YAML. Данные хранятся в именованном volume `simulator_data`; `docker compose down` сохраняет его.

Это Compose только симулятора. Модель, Runtime и установщик еще не реализованы.

## Демонстрационные данные

При первом старте новой базы создаются:

- 6 товаров: бумага, ручка, блокнот, папка, клавиатура и мышь;
- 3 магазина: `store-1`, `store-2`, `store-3`;
- 3 поставщика с демонстрационными контактами в домене `.example`;
- 18 записей остатков, включая нулевые;
- 9 неизменяемых тестовых событий продаж/возвратов для проверки отчетов и границ периода.

Например, `SKU-001` / `product-1` в `store-3` имеет остаток 12 и двух поставщиков. Даты продаж фиксированы в августе–октябре 2026 года, чтобы результат не зависел от дня запуска.

Повторный запуск не добавляет данные заново и не восстанавливает удаленные записи. Для независимого нового набора используйте другой путь базы. CRUD остатков не проводит продажи; исторические события являются отдельными тестовыми fixtures.

## CRUD

Для каждого ресурса поддерживаются:

| Метод | URL | Результат |
|---|---|---|
| `GET` | `/api/v1/{resource}` | Список `items`, `total`, `limit`, `offset` |
| `POST` | `/api/v1/{resource}` | Создание, статус 201 |
| `GET` | `/api/v1/{resource}/{id}` | Одна запись |
| `PATCH` | `/api/v1/{resource}/{id}` | Частичное изменение |
| `DELETE` | `/api/v1/{resource}/{id}` | Удаление, статус 204 |

Ресурсы: `products`, `stores`, `suppliers`, `inventory`. `GET /products?q=бумага` ищет по названию/артикулу без учета регистра, включая русский язык. Для остатков предусмотрены фильтры `store_id` и `product_id`. Максимальный `limit` — 200.

Тело создания товара:

```json
{
  "sku": "NEW-001",
  "name": "Демонстрационный товар",
  "price": "199.90",
  "unit": "шт.",
  "supplier_ids": ["supplier-1"]
}
```

Тело создания остатка:

```json
{
  "product_id": "product-1",
  "store_id": "ID нового магазина",
  "quantity": 5
}
```

ID генерирует сервер. SKU нормализуется к верхнему регистру и уникален. Пара товар/магазин у остатка уникальна. Количество — целое неотрицательное число. Деньги принимаются с точностью до двух десятичных знаков, хранятся в целых копейках и возвращаются строками в RUB.

Неизвестные поля, пустые PATCH и явный `null` отклоняются. Неизвестная запись или ссылка дает 404, нарушение уникальности либо удаление связанного товара/магазина — 409, неверный ввод — 422. Изменение товара и связей с поставщиками атомарно. Удаление поставщика удаляет его связи с товарами; удаление товара/магазина с остатками или историей продаж запрещено.

## Операции будущего ассистента

| Operation ID в OpenAPI | Запрос |
|---|---|
| `get_stock` | `GET /api/v1/business/stock?sku=SKU-001&store_id=store-3` |
| `get_suppliers` | `GET /api/v1/business/suppliers?product_id=product-1` |
| `get_sales_report` | `GET /api/v1/business/sales-report?store_id=store-3&date_from=2026-09-01&date_to_exclusive=2026-10-01` |

Бизнес-операции возвращают envelope `status`, `source_id`, `fetched_at`, `data`. Время `fetched_at` означает время получения ответа от симулятора. Отсутствующая запись об остатке дает 404 и отличается от существующей записи с количеством 0.

Период отчета — `[date_from, date_to_exclusive)` в часовом поясе Москвы. Максимальная длина — 366 дней; поддерживаются 1970–2100 годы. Сумма продаж минус сумма возвратов дает чистую выручку. Это учебная модель: налоги, себестоимость и бухгалтерские проводки не учитываются. Цена фиксируется в событии продажи; изменение текущей цены товара не меняет историю.

Для `store-3` за сентябрь 2026 года: продажи **2654.20 RUB**, возвраты **59.90 RUB**, чистая выручка **2594.30 RUB**. Известный магазин без событий за период дает нулевой отчет; неизвестный магазин — 404.

CRUD предназначен для настройки локального стенда. Роли и авторизация будущего Runtime здесь еще не реализованы; коннектор ассистента должен получить только три бизнес-операции чтения. Симулятор по умолчанию слушает loopback и использует исключительно синтетические данные.

## Тесты

Из корня репозитория:

```powershell
.\.venv\Scripts\python.exe -m pytest tools/business-api-simulator/tests
```

Проверяются CRUD, откаты транзакций, уникальность, связи, поиск, строгая валидация остатков/денег, сохранение после перезапуска, точные суммы и московские границы отчетного периода. Каждый тест использует отдельную временную базу.
